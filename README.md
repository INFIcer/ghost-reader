# Ghost Reader（虚影读取器）

**版本 1.2.1** · 适用于 Factorio 2.1（含太空时代）

在原版游戏中，建设机器人的任务无法通过信号获取，但这对于自动化建设非常重要，本 mod 着重解决此问题。mod 添加一个新实体，它读取所在表面或所在物流网络范围内的虚影数量并输出为电路信号，可使用 GUI 进行详细配置。支持调整筛选模式（实体|地格|升级|物品）、数量模式（供给请求|回收请求）与品质筛选。

---

# 面向普通玩家

## 这个 Mod 是做什么的

在原版游戏中建设机器人的任务无法通过信号获取，但这对自动化建设非常重要，该mod着重解决此问题。Ghost Reader 把这些请求汇总成一个清晰的物品清单，并作为电路信号输出，方便你自动化计算缺料、驱动显示面板或物流请求。

它读取四类请求，并分别统计**供给**和**回收**两个方向：

| 类型 | 供给 | 回收（会被拆除/回收） |
| ---- | ---- | ---- |
| 实体 | 待建的实体虚影 | 被标记拆除的实体 |
| 地格 | 待铺的地形虚影 | 被标记拆除的地格 |
| 升级 | 升级后的目标实体 | 升级替换下的原实体 |
| 物品 | 请求送入的物品 | 被拆除实体内部已有的物品（含插件）、回收储物格请求（移除物品）、环境实体（树/鱼/岩石等）的回收产物、落地物品 |

> **关于「物品」的说明**：这里的【物品】指的是在**实体上的储物格**进行**幽灵操作**（远程视图里直接设置）时产生的物品请求，由**建设机器人**响应。它**不是**指物流机器人响应的物品物流请求。

- **供给** = 建设机器人工作**缺少**的物品。
- **回收** = 会被建设机器人**拆除或回收**的物品。

## 如何解锁

- 研究科技「虚影读取器」（前置科技：**建设机器人**）。

## 如何使用

1. 放置一个「虚影读取器」。
2. 把它用红/绿线接入电路网络。
3. 在读取器上点击打开 GUI 面板，设置检索范围、筛选模式、数量模式和品质筛选。
4. 电路网络里就会出现各物品的信号，信号值按当前数量模式计算。

## GUI 面板说明

- **检索范围模式**
  - `表面`：扫描整个星球表面上的全部请求。
  - `物流网络`：只扫描读取器所在的物流网络（建设区域）内的请求。
- **当前范围**：实时显示当前生效的范围。
  - 表面模式：显示所在地，如 `【新地星】`。
  - 物流网络模式：显示 `【网络#id】`。
- **筛选模式**
  - `全部`：实体 + 地格 + 升级 + 物品。
  - `实体` / `地格` / `升级` / `物品`：只计对应类别。
- **数量模式**
  - `供给 - 回收`：输出供给减回收的净值（可为负，用于求净缺口）。
  - `仅供给`：只输出供给数量。
  - `仅回收`：只输出回收数量。
- **品质筛选**
  - `全部`：不按品质过滤。
  - 具体品质：只输出该品质的物品。

## 计算细节（重要）

- **物流网络模式**下，实体、地格、升级和物品都按各无人机平台（roboport）的**建设区域**（绿色区域）的**并集**计算。因为只有请求实体（或虚影）的中心点落入建设区域内才能被建设机器人响应，所以判断条件与之保持一致。
- **物流网络模式**下，读取器自身必须位于某个无人机平台的**供应区域**（橙色区域）内，才能被判定为「属于某个物流网络」。
- 属于**中立/敌方阵营**的目标（树、岩石、落地物品、虫巢等）本身不会有物流网络，它们按位置计入覆盖到它们的玩家阵营物流网络；而玩家阵营的实体只按自己阵营的建设区域计算。
- 移动实体（如：坦克、蜘蛛机甲）上的物品请求同样会被计入。
- 若某个容器实体（如箱子）被标记拆除，它**内部已有的物品和插件**会归类到「物品」类别记为回收，同时其上的临时物品请求会作废（不重复计数）。

# 面向 Mod 开发者

本部分面向希望快速理解该 Mod 结构、进而修改或借鉴的开发人员。

## 结构总览

- **data.lua** —— 声明新实体。基于原版恒压器（constant-combinator）原型复制出一个同名自定义实体，并把它内部的贴图引用重定向到本 Mod 自带的图形资源（不依赖 `__base__`），同时注册对应的物品、配方和科技。
- **data-updates.lua** —— 为读取「物品请求」做铺垫。它给原版的 item-request-proxy 原型挂上一个创建效果，使该实体每次被创建时都能向脚本发送一个事件。
- **control.lua** —— **入口文件**：按依赖顺序 require `dop2/` 下的各模块，注入跨模块依赖，最后调用 `events.register()` 完成事件注册。
- **dop2/** —— 全部运行时逻辑，按职责拆成 14 个模块（见「文件结构」）。

> `dop/` 目录是重构前的旧实现，仅作备份保留，当前不参与运行；想切回旧版把 `control_dop.lua` 的内容复制进 `control.lua` 即可。

## 模块划分（dop2/）

| 模块 | 职责 |
| ---- | ---- |
| `lib.lua` / `enum.lua` | 全局常量（`READER`、计数项名、`QUALITY_ALL`）、工具函数与枚举（`change_type` / `range_mode` / `filter_mode` / `count_mode`）。加载期即写入全局表，故必须最先 require |
| `config.lua` | 读取器配置（范围/筛选/数量/品质），按实体单位号存 `storage.readers` |
| `counter.lua` | 两级计数表：物品名 → 品质名 → 数量 |
| `count_item.lua` | 计数项：`change_type` → `counter` |
| `item.lua` | 物品/地格解析、实体携带物品统计、IRP 明细提取 |
| `region.lua` | 归属地（表面 / 物流网络），维护其成员并合并计数 |
| `meta.lua` | 实体元信息与计数项（注册号 → 元信息），读取器输出组装 |
| `snapshot.lua` | 指纹快照轮询（内容物 / 位置 / IRP） |
| `gui.lua` | 读取器面板与悬浮提示 |
| `bplib.lua` | 蓝图 tags 配置持久化（依赖 bplib） |
| `paste.lua` | 复制粘贴：与原版恒压器隔离 + 读取器之间继承配置 |
| `events.lua` | 事件层 + `on_tick` 管线 + 初始化 / 全量重建 |

## 核心数据流

1. **配置**：每个读取器按「表面」或「所在物流网络」决定读取哪个归属地，另有筛选/数量/品质三个过滤器。
2. **计数实体**：每个被关注的实体（虚影、被标拆除的实体、被标升级的实体、IRP 目标容器、读取器自身、无人机平台自身）都有一份元信息，里面按用途存若干**计数项**。
3. **归属地合并**：计数实体同时归属「所在表面」与「所在物流网络（可能有多个）」；归属地把成员的所有计数项合并成一张总表。
4. **脏标记管线**：事件只置位脏标记（不直接算），`on_tick` 里按固定顺序统一结算：归属地重解析 → 计数传播 → 归属地合并 → 读取器归属地 → 读取器输出。
5. **信号输出**：读取器读自己归属地的合并表，按三个过滤器过滤（回收类在净模式下取负），写进恒压器的插槽；插槽满了自动新建 section（每 section 上限 1000，引擎硬上限）。

## 计数项与类别

计数项是「按 `change_type` 分类的计数表」，读取器按类别过滤后输出。一个实体上可能同时存在多项：

| 计数项 | 内容 | 类别 |
| ---- | ---- | ---- |
| `ghost` | 实体虚影 / 地格虚影 | 实体供给 / 地格供给 |
| `upgrade` | 升级标记：目标实体（供给）与原实体（回收） | 升级供给 / 升级回收 |
| `deconstruction-entity` | 被标拆除的实体本身（同时充当「已标记拆除」的判据） | 实体回收 |
| `deconstruction-tile` | 被标拆除的地格（由 deconstructible-tile-proxy 代表） | 地格回收 |
| `deconstruction-inventory` | **有内部存储**的实体里的物品：机器人要一件件搬，由内容物快照轮询跟踪 | 物品回收 |
| `deconstruction-instant` | **瞬间拆除**类（环境实体、落地物品）的回收产物：标记时一次算清 | 物品回收 |
| `irp<注册号>` | IRP 的请求（供给）与回收计划（回收），记在目标容器上 | 物品供给 / 物品回收 |

「内容物」因此分成两类，对应 `item.lua` 里两对函数：

- `has_inventory_contents` / `inventory_contents`：有储物格，或传送带/机械臂把货放在运输线/手持栈上 → 建**内容物快照**，机器人搬走一件就同步一次。
- `is_instant_recycle` / `instant_recycle_items`：环境实体（挖掘产物）与落地物品（stack）→ **标记时计一次**，不建快照（一大片森林被标拆除时不产生任何快照）。

其余采集来源：传送带运输线、机械臂手持栈、容器库存、IRP 的请求与回收明细。

## 归属地（region）模型

- 归属地由引擎对象派生，用 `register_on_object_destroyed` 的注册号做键：**物流网络归属地** 与 **表面归属地** 两种。
- 计数实体的归属地 = 覆盖它位置的全部物流网络 + 所在表面；读取器按范围模式**二选一**读取。
- 阵营规则：属于**有玩家的阵营**的实体只查自己阵营的建设区域；属于**没有玩家的阵营**（neutral 的树/岩石/落地物品、enemy 的虫巢等）则遍历所有玩家阵营的建设区域——它们自身阵营没有物流网络，只查自己会一个都取不到。
- 网络**合并**时引擎会为消失的网络触发 `on_object_destroyed`（`type=logistic_network`，`useful_id` 是 network_id），据此回收归属地并让成员重解析。
- 网络**分裂**时引擎不销毁任何网络对象（存活那半沿用原 id，裂出去那半是新 id），所以由**平台被拆**这一侧反推：把该平台原网络归属地的全部成员标脏重解析。

## 快照子系统

有些变化没有原生事件（机器人逐步搬走箱内物品、实体被拖走、IRP 请求被部分供应），用「快照 + 指纹」轮询：

- 三类快照：内容物（`inventory_contents`）、位置（格点指纹）、IRP（请求/回收明细各一个 counter）。
- 创建时立刻跑一次（`previous = nil`），所以**事件层只负责建快照**，"创建即完成首次计数"，不需要自己写这些计数项。
- 轮询调度：每 tick 有固定预算（默认 8 个）；两个世代（活跃 / 不活跃）各是一组「上轮已查 / 本轮已查 / 本轮未查」三表轮转，快照连续 30 次无变化就转入不活跃世代，查得更稀。
- 待查队列用**游标**推进（不从队首 `table.remove`），删除快照用**惰性标记**（`dead`），避免批量销毁时出现与队列长度相关的周期性卡顿。

## 事件驱动更新

Mod 优先事件驱动，而非每帧轮询：

- 虚影创建/销毁、拆除/升级标记、平台增删、IRP 创建、配置变更等都只置脏标记；`on_tick` 统一结算一次。
- 归属地自身被销毁（网络合并）、平台被拆导致网络收缩时，会把相关成员标脏重解析。
- 打开的面板每帧跟随刷新，但**信号表带指纹门**：内容没变就不重建 GUI 元素。

## 蓝图与复制粘贴

- **蓝图**：通过 bplib 的自定义事件把读取器配置写进蓝图实体的 tags（`gr_mode` / `gr_filter` / `gr_count` / `gr_quality`）；放置时按位置记下待应用配置（`pending_tags`），虚影建成时消费并留下 `ghost_cfg`，供同位置的真实读取器继承。
- **复制粘贴**：把读取器与原版恒压器（同为 constant-combinator）隔离——复制读取器时不把它的输出信号当成恒压器配置带走；读取器之间（含虚影）则继承配置。

## 初始化与全量重建

- 模块级注册表（元信息/归属地/快照）不落 storage，读档后为空，故 `on_load` 只置 `needs_rebuild`，首帧执行一次全量重建：清空注册表 → 表面归属地 → 平台 → 读取器 → 虚影（实体/地格）→ 升级标记 → 拆除标记 → 地格代理 → IRP。
- `on_configuration_changed` 直接重建。重建复用与事件路径完全相同的函数，保证两条路径登记出的状态一致。

## 性能要点

- 全程脏标记 + 每帧一次结算，几乎不做全表面扫描；平台的建设区域扫描按类型过滤（只登记虚影/地格虚影/地格代理/IRP 与已标记拆除/升级的实体），不会把区域里的树、石头也登记成计数实体。
- 归属地合并只在归属地被标脏时重算，成员增删只做哈希比对就地增删。
- 快照有每帧预算与活跃/不活跃世代，稳态开销与快照总数无关。
- 面板刷新有指纹门，信号不变时不产生 GUI 元素增删。

## 两份实现容易踩的坑（记录备查）

- **不要把原型对象当表键**：`prototypes.item["iron-plate"]` 每次调用返回的是**不同 userdata**（`a == b` 为真是靠引擎的 `__eq`，而 Lua 表键只看原始身份、不走 `__eq`），用它当键会让同一个物品永远合不到一起（多堆同类物品只剩一堆的数量）。所以计数表/计数项的键一律用**名字字符串**，`counter.lua` 收到非字符串会直接报错，`ensure_quality` 只接受品质名。
- **2.x 的对象方法是从对象上取出的绑定闭包**：所以全项目写 `parent.add{...}`、`bp.set_stack{...}`（点号，不带 self）。用 `pcall(obj.method, obj, {...})` 多传一个 self 会报 `Expected 1 argument but 2 were given`。
- **`require` 只能在解析 control.lua 期间调用**，运行期调用会报 `Require can't be used outside of control.lua parsing`。`meta` 与 `snapshot` 互相依赖，因此由入口在两者加载完后调用 `meta.inject_snapshot(snapshot)` 注入，而不是在函数里延迟 require。
- **`LuaLogisticSection.filters_count` 是「当前已有多少个过滤器」，不是插槽容量**（清空后恒为 0）；常量箱 section 的插槽上限是 1000，越界 `set_slot` 会直接报错。
- **bplib 事件里的坐标是它内部的数组形式 `{x, y}`**（类型注解写的是 `MapPosition`，容易踩），两种形式都要认。
